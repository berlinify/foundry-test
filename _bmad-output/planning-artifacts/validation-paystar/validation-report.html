Fair — strong design, stale inputs

This is a well-made architecture document. The invariants are enforced rather than aspirational, the multi-tenancy design closes the two ways RLS is normally defeated, and the payment-durability chain is careful work with the authority question properly pinned. Most of what a reviewer would attack, it has already closed.

Its defects are not in reasoning. They are in inputs and arithmetic: three [CONFIRMED] technology pins are end-of-life as of today, one confirmed decision deletes a bounded context the parent PAD defines, and the delivery plan consumes all 26 weeks of the six-month budget with zero slack against a team size that appears once in passing and is absent from the assumption register.

Fixing the version pins is nearly free today and expensive after Wave 0 builds on them.

high

targetSdk 32 is unpublishable on Google Play

§1.1 D-14, §3.3

From 2026-08-31 new apps and updates must target API 36; existing apps need API 35+ to reach new users. The decision also conflates two settings: minSdk 27 is what delivers the stated Android 8.0 baseline and is correct; targetSdk does not affect device reach and is given no rationale. If distribution is OTA-only (§12.6) the policy does not bind — but the TAD never states the distribution channel.

Fix: state the channel. If Play is in scope at any horizon, raise targetSdk and budget behaviour-change testing. Keep minSdk 27.

high

No rule on whether cross-module references are real database FKs

§4.1, §7.1

§7.1 covers FK naming, not enforcement. Two teams can each obey every §4.1 rule and still produce inconsistent referential guarantees — and a real FK across a module boundary blocks the later service extraction that §4's stated goal and the Dedicated-SaaS horizon both depend on.

Fix: state that cross-module references are logical ids with no database-level FK, integrity enforced in the owning module — or state the inverse. Either is defensible; silence is not.

high

Tenant context has no defined propagation into queued jobs or the outbox relay

§5.2, §5.5, §10

SET LOCAL app.tenant_id is transaction-scoped and correct for HTTP requests. §5.5 extends isolation to Redis, Kafka, object storage and logs — but no line covers the database connection of a background worker. A queued job opens a fresh connection with no tenant set, so RLS reads return empty. The dangerous compliant response is a worker connecting through the §5.4 platform-scope bypass role, turning an audited escape hatch into a routine background path.

Fix: mandate tenant_id on every job and the relay, re-established via the same middleware; forbid the bypass role to queue workers by configuration; add an in-job RLS isolation test to §16.4.

What the document already gets right

These attacks were attempted and failed — the document closes them:

  • Payment authority on unknown — §9.2 step 7 makes Payment Core authoritative; §9.5 forbids reconciliation from altering a succeeded/failed payment without an audited manual action.
  • Receipt printed before sync — permitted, but annotated "در انتظار همگام‌سازی" with a pending-sync indicator. The ambiguity is surfaced to the human, not hidden.
  • Two devices claiming one payment request — SELECT … FOR UPDATE SKIP LOCKED (§9.3).
  • Duplicate event processing — at-least-once plus processed_events dedupe (§10.2).
  • Kafka as a correctness dependency — removed by the transactional outbox, which also neutralises assumption A-02 (§10.2).

Also notably strong: deptrac as automated boundary enforcement rather than review convention (§4.1) · FORCE ROW LEVEL SECURITY plus a non-superuser non-owner role, closing both silent-RLS-bypass paths (§5.2) · naming the RLS isolation test and the process-death test as "the two that will save the project" (§16.4) · a complete operational envelope (§3.4, §15, §16, §17) that domain-focused drafts routinely skip.
